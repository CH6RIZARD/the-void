## verdict 0: AMENDED

1. §7 WRONG three.js semantics — BackSide DOES flip normals. three defines FLIP_SIDED whenever material.side === BackSide (WebGLPrograms: `flipSided: material.side === BackSide`), and defaultnormal_vertex negates: `#ifdef FLIP_SIDED transformedNormal = - transformedNormal;` — in r128 and every modern release alike. The atmosphere shell is therefore lit with INWARD (negated) normals, not "the geometric outward normals". A rebuild following the spec as written produces a different rim-glow falloff. Fix: cull front faces AND negate the normal before lighting.

2. §5 OMISSION / overclaim — max anisotropy is NOT set on the common path. Only the two loadEarthTexture() paths in textures.ts set dt.anisotropy. The warm "born textured" path (globeScene.ts lines 305-322), which the spec itself (§10) describes as the normal case once the boot warmup has run, builds its DataTexture with NO anisotropy (default 1) and never calls loadEarthTexture, so the shipped look on a warmed launch has no anisotropic filtering at all. The spec's "max anisotropy the GPU reports (this is most of the perceived sharpness at the limb)" describes the cold/fallback path only. The rebuild must pick one (and setting max anisotropy everywhere arguably fixes a bug, but is not pixel-identical to today's warm-launch output).

3. §8 nuance — uProj's "drawingBufferHeight" is the buffer height captured ONCE at scene creation (const bufH, globeScene.ts line 49-50); resize() updates the fake canvas and raster but never the value projScale() uses, so after a rotation uProj is stale. Also "intentionally uses the full buffer height" is editorial: the code comment (line 290) derives the formula from Sprite parity, written when render height == buffer height; with RASTER_CAP active the markers draw ~density/1.6× larger relative to the globe than on the web — replicate it for app parity, but it is a web/APK divergence, not a documented intention.

4. §4 internal inconsistency / depth nuance — §4 says stars are hidden "by the globe's opaque draw + depth", §10 says "draw order + the globe's opaque overdraw". The code comment (line 161: "drawn first: the globe paints over them without a depth test") and the broken-depth constraint make §10 the authoritative behavior. They differ visibly: with a working depth buffer (the original web look), a star that lands between the camera and the planet is drawn first, wins the depth test, and punches through the globe as a ~1px dot; with order-only overdraw the globe paints over it. A rebuild honoring the no-depth-reliance contract should use order-only (§10) and drop §4's "+ depth" wording.

Minor, for completeness: §6's rim attenuation — the shipped modern branch uses the constant 0.933 with decay 0 (times three's modern cutoff smoothing, ≈0.996 at d≈6.7), whereas the spec's r128 formula max(0, 1−d/100) varies per fragment ≈0.923–0.943 across the globe. The spec's formula is the correct r128 target it declares, but it is not bit-identical to the current app's point-light falloff.
