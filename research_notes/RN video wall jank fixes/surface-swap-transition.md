# Locked-60fps translateX swipe between two heavy mounted siblings (live-video wall <-> WebGL globe) on low-end Android, RN 0.86 new arch

## Q1. What work fires when heavy offscreen-but-mounted siblings move; SurfaceView vs TextureView inside translated containers

### Takeaway
Since Android 7.0, translating/scaling a SurfaceView is synchronized with normal View rendering and does not by itself cause artifacts — and SurfaceView is cheaper than TextureView for video because it composites in dedicated hardware with fewer copies. The real per-frame cost of sliding a mounted subtree in RN new arch is not Android recomposition of the players; it is Reanimated's shadow-tree commit path (Yoga + prop diff + mutation) unless the synchronous-UI-props fast path is enabled.

### Cited Findings
- "Starting in platform version Android 7.0 (N), SurfaceView's window position is updated synchronously with other View rendering. This means that translating and scaling a SurfaceView on screen will not cause rendering artifacts. Such artifacts may occur on previous versions of the platform." — [Android 7.0 for Developers / SurfaceView docs](https://developer.android.com/about/versions/nougat/android-7.0); AOSP commit ["Document that SurfaceView is synchronous in N"](https://android.googlesource.com/platform/frameworks/base/+/6ee192f%5E%21/)
- "When rendering video or 3D content, apps with scrolling and animated video position use less power with SurfaceView than with TextureView"; SurfaceView "is composited in dedicated hardware, separately from app window content... it makes fewer intermediate copies than TextureView." — [Android 7.0 for Developers](https://developer.android.com/about/versions/nougat/android-7.0)
- Pre-N (and still folklore-level advice): SurfaceView inside scrollable/animated containers shows "stretching, jumping, blinking" and black flashes; black flash when switching videos is a SurfaceView rendering artifact that TextureView avoids. — [SurfaceView intro article (dmytrodanylyk)](https://github.com/dmytrodanylyk/dmytrodanylyk/blob/gh-pages/articles/surface-view-intro.md); [Xibo forum on video-transition black screens](https://community.xibo.org.uk/t/video-transitions-black-screen/5160)
- react-native-video exposes this choice directly: `surfaceType` (Android-only, default `'surface'`): "'surface' uses SurfaceView and is more performant but cannot be animated or transformed, while 'texture' uses TextureView, is less performant, but can be animated and transformed." — [react-native-video VideoView docs](https://www.mintlify.com/TheWidlarzGroup/react-native-video/core/video-view)
- On RN new arch, "every frame, Reanimated's worklet computes new values and commits a prop update through the shadow tree, which runs Yoga layout, prop diffing, and view mutations" even for transform/opacity; the `ANDROID_SYNCHRONOUSLY_UPDATE_UI_PROPS` feature flag "short-circuits this by pushing visual prop updates directly to the UI layer, skipping the layout pass entirely" (Moto G8 Plus, 50 views: Reanimated SV 11.87ms -> 10.57ms, -11%). — [Expo blog: The real cost of React Native animations](https://expo.dev/blog/the-real-cost-of-react-native-animations-benchmarking-every-approach)
- Black-flash workaround when a SurfaceView first attaches: place a View with identical bounds and matching background color behind it so the initial black surface never shows. — [LiveCode forum: Android adding SurfaceView causes black flash](https://forums.livecode.com/viewtopic.php?p=88706)

### Inferences
- The react-native-video doc's "SurfaceView cannot be animated" is conservative/legacy guidance: Android's own docs say translate/scale is safe on N+ (min SDK for RN 0.86 is well above N). Rotation and alpha on SurfaceView remain unsupported, but a pure translateX pager does not need them. Test `surfaceType='surface'` sliding on the actual MediaTek clones first; fall back to `'texture'` only if the specific OEM compositor glitches — the clones' HWC quality is the unknown, not the API contract.
- Black flashes are an attach/detach and surface-recreation problem, not a translation problem. Keeping both siblings mounted (as planned) avoids the main black-flash trigger; never unmount/remount the video views across the swipe, and keep an opaque backing view behind each player.
- The per-frame "recomposition" fear is misplaced: translating a parent doesn't re-run React render or re-measure children; the cost centers are (a) Reanimated's commit path (fixable with the sync-props flag), and (b) SurfaceLinger — each SurfaceView punches a hole whose position SurfaceFlinger must update per frame; many small SurfaceViews moving at once multiplies compositor layers (see Q4).

### Gaps
- No authoritative source found on the per-frame SurfaceFlinger cost of moving N simultaneous SurfaceViews (a video wall) on low-end MediaTek HWC — this needs on-device testing with `adb shell dumpsys SurfaceFlinger` / overdraw tooling.
- No RN-specific published measurement of TextureView vs SurfaceView wall translation FPS.

## Q2. Reanimated patterns for gesture-driven transitions that never touch the JS thread, and what breaks that contract

### Takeaway
Pan gesture callbacks are worklets on the UI thread by default; drive a single shared value from the Pan gesture and map it to `transform: translateX` in `useAnimatedStyle` on both siblings. The contract breaks when you animate layout props, read shared values from JS, call `runOnJS`/`scheduleOnRN` per-frame, or recreate gesture/style objects on re-render.

### Cited Findings
- Worklets are compiled and run on the UI thread, separate from JS; gestures/scroll/drag should be per-frame work in worklets with shared values; any JS-side effect (navigation, analytics, state set) must go through `scheduleOnRN` and hops to the JS thread. — [Shopify: first look at Reanimated 2](https://shopify.engineering/first-look-reanimated-2); [tothenew: Mastering React Native Reanimated](https://www.tothenew.com/blog/?p=78074)
- "Reading shared values is allowed only from worklets running on the UI thread." Reading on the JS thread "will get blocked until the value is fetched from the UI thread" — a synchronous JS<->UI stall. — [Reanimated performance guide](https://docs.swmansion.com/react-native-reanimated/docs/guides/performance)
- "Animating non-layout properties (like transform, opacity or backgroundColor) is generally more performant than animating styles that affect layout" because layout styles force recalculation each frame; recommendation to prefer translateX/translateY over top/left. — [Reanimated performance guide](https://docs.swmansion.com/react-native-reanimated/docs/guides/performance)
- Reanimated guide: "animate no more than 100 components for low-end Android devices"; memoize frame callbacks and gesture objects to prevent recreation; verify in release mode (debug inflates cost: 28.62ms debug vs 11.87ms release at 50 views). — [Reanimated performance guide](https://docs.swmansion.com/react-native-reanimated/docs/guides/performance); [Expo benchmark blog](https://expo.dev/blog/the-real-cost-of-react-native-animations-benchmarking-every-approach)
- Measured Android frame costs (Moto G8 Plus, release): Reanimated shared values 7.25ms @10 views, 11.98ms @100, 39.94ms @500 — the 16.67ms budget dies well before 500 animated views. — [Expo benchmark blog](https://expo.dev/blog/the-real-cost-of-react-native-animations-benchmarking-every-approach)
- Feature flags `ANDROID_SYNCHRONOUSLY_UPDATE_UI_PROPS` (and iOS twin) push non-layout prop updates directly to the UI layer, skipping shadow-tree commit; opt-in due to potential visual bugs. Scroll-related flicker/FPS fixes additionally need RN 0.80/0.81+ and Reanimated 4.2+ with `USE_COMMIT_HOOK_ONLY_FOR_REACT_COMMITS`. — [Reanimated performance guide](https://docs.swmansion.com/react-native-reanimated/docs/guides/performance)

### Inferences
- Correct shape for this pager: ONE animated container per side (or one parent strip) whose style is `transform:[{translateX: progress.value}]`; never animate each tile. Two animated views = far inside the 100-component budget.
- Contract-breaker checklist for the drag window: no `.runOnJS(true)` on the Pan gesture; no `runOnJS`/`scheduleOnRN` inside `onUpdate` (only at `onStart`/`onFinalize`, and even there defer — see Q5); no `measure()` in the hot path (take measurements before the gesture or use known screen width); no reading `progress.value` from JS (it blocks); no React state set in gesture callbacks; gesture and animated styles wrapped so parent re-renders don't recreate them.
- Settle with `withSpring`/`withTiming` started inside `onEnd` (worklet) — the whole gesture->settle lifecycle then never touches JS. The only JS hop is one deferred "activeSide changed" notification after settle.
- Enable `ANDROID_SYNCHRONOUSLY_UPDATE_UI_PROPS` for this app: the pager animates only transform (non-layout), which is exactly the fast path, and it removes per-frame Yoga/commit cost on the two full-screen subtrees.

### Gaps
- No published numbers for the worklet first-run compilation cost at gesture start (a known anecdotal source of first-gesture jank); mitigate by running the gesture path once invisibly at mount, but I found no citable source quantifying this.

## Q3. Freezing the hidden side: react-freeze / freezeOnBlur semantics, pausing GL loop and video players during the drag without gesture-start stutter

### Takeaway
react-freeze suspends React reconciliation of a subtree via Suspense while keeping native views and state alive — but its placeholder is `null` by default, which unmounts the native views from layout, so it must NOT wrap a side that has to stay pixel-visible mid-swipe; it's for the fully-hidden steady state, flipped after settle, not at gesture start. Pausing players/GL at gesture start puts that work on the exact frame the gesture begins — the evidence says pause nothing on the gesture frame; pause after settle, or stagger the pauses across frames.

### Cited Findings
- react-freeze uses React Suspense (React 17+) to stop rendering/reconciliation of a subtree while "frozen components are not unmounted when they are replaced with a placeholder view" — React state, scroll position, inputs, loaded images retained; renders resume with latest state on unfreeze. Gotchas: default placeholder is `null` (layout collapses unless placeholder matches dimensions); "only freeze components invisible to users"; subscriptions/selectors keep running, only renders are suspended. — [react-freeze README](https://github.com/software-mansion/react-freeze); [SWM blog: Experimenting with react-freeze](https://swmansion.com/blog/experimenting-with-react-freeze-71da578e2fa6)
- react-native-screens (3.9+) integrates react-freeze for navigation; purpose is to skip wasted update time on invisible screens/tabs. — [SWM blog](https://swmansion.com/blog/experimenting-with-react-freeze-71da578e2fa6); [react-freeze on npm](https://npmjs.com/package/react-freeze)
- A reported new-arch pitfall (low-confidence source, a third-party recipes dump for the OneKey app): with `freezeOnBlur` on iOS native tabs, the "unfreeze -> Fabric commit pipeline can fail to flush, leaving the UI showing pre-freeze stale content until a touch event forces React to re-evaluate"; their fix was disabling freezeOnBlur there. — [OneKeyHQ app-monorepo UI recipes](https://skills.cat/skills/onekeyhq/app-monorepo/skillshare-skills-1k-ui-recipes)
- expo-gl `GLView`: "On mounting, an OpenGL ES context is created. Its drawing buffer is presented as the contents of the View every frame" — the app owns the rAF loop, so the app can simply stop scheduling frames. — [Expo GLView docs (SDK 57)](https://docs.expo.dev/versions/v57.0.0/sdk/gl-view.md)
- Platform precedent for pausing GL loops: GLKViewController exposes a `paused` bool and auto-pauses the render loop on resign-active / resumes on active — pause/resume of a GL loop is a supported, cheap operation (stop scheduling, keep context alive). — [GLKViewController docs](https://developer.apple.com/documentation/glkit/glkviewcontroller.md)
- ExoPlayer: instances must be accessed from a single thread (normally main); operations post messages to an internal playback thread via a message queue — so `pause()` itself is cheap on the caller thread, but N calls still queue N main-thread dispatches plus downstream audio/renderer work. — [Media3 ExoPlayer interface docs](https://developer.android.google.cn/reference/kotlin/androidx/media3/exoplayer/ExoPlayer)
- Cross-stack evidence on phase-aligned player work: with 24 simultaneous players, staggering their work against running them in-phase dropped frames overrunning the 60Hz budget from ~50% to under 1%, and roughly halved p99 main-thread work — "staggering costs more in aggregate than it saves; it buys a flatter, more predictable per-frame load." (Unity + HAP codecs, not ExoPlayer — treat as principle, not benchmark.) — [Bluecadet: Playing many videos at once](https://unity.bluecadet.com/hap/performance/)
- InteractionManager: "schedule tasks to run after any interactions/animations have completed"; touch handling treats active touches as an interaction and delays callbacks until touches end; deprecated in RN 0.81+ in favor of `requestIdleCallback`. — [RN 0.86 InteractionManager docs](https://reactnative.dev/docs/0.86/interactionmanager)

### Inferences
- Layered freezing strategy that avoids gesture-start stutter:
  1. During steady state: hidden side wrapped in `<Freeze freeze={!isActive}>` only AFTER it is fully offscreen post-settle (flip the flag from a deferred callback, not in `onEnd` worklet directly). Both native view trees stay mounted; only React updates stop.
  2. At gesture START: do nothing. Unfreeze the incoming side via a single deferred JS task (`scheduleOnRN` -> `requestIdleCallback`/microtask), accepting that the incoming side shows its last-rendered (retained) native frame during the drag — react-freeze keeps native views and their last pixels, which is exactly the "warm snapshot" wanted. Do not pause the outgoing side's players mid-drag.
  3. After settle: pause the now-hidden side's GL loop (stop scheduling rAF; keep context) and pause/mute its players — staggered one or two per frame if pausing all at once measurably spikes (Bluecadet principle).
- Caution on react-freeze + Fabric: the placeholder-null issue means wrapping the whole sibling in Freeze while it must still be visible during a future swipe-back is wrong. Two safe options: (a) freeze only the *children/update sources* (feed stores, effects) not the visual tree; (b) keep Freeze but unfreeze before the gesture can start (e.g., on touch-down of the pager region via a cheap deferred flag), so by the time translateX moves, the subtree renders again. Given the stale-content Fabric report above, verify unfreeze-flush on the actual devices.
- For the GL globe specifically: don't tear anything down — throttle. During the drag, drop the globe loop to 0fps (skip frames) only if it's the OUTGOING side; if it's the incoming side, keep it at full rate since it is becoming visible. Frame-skipping a self-owned rAF loop costs one boolean check; there is no native pause/teardown work to land on the gesture frame.

### Gaps
- No authoritative doc on react-native-screens `freezeOnBlur` internals under Fabric specifically (search results were dominated by low-quality aggregators); the Fabric stale-flush report is single-sourced and iOS-native-tabs flavored. Needs on-device verification.
- No published measurement of ExoPlayer `pause()` main-thread cost per player on low-end devices; the stagger numbers are from a different stack.

## Q4. GPU overdraw during the transition: two full screens composited while sliding, Mali cost, opaque backgrounds/clipping, renderToHardwareTextureAndroid

### Takeaway
During the drag you inevitably shade up to ~2x screen pixels; on tile-based Mali GPUs the fix is making every layer opaque (transparent layers defeat Mali's hidden-surface pixel-kill), removing redundant backgrounds, and minimizing full-screen layers. `renderToHardwareTextureAndroid` is explicitly the wrong tool for a translateX slide whose children fill/overflow bounds — and SurfaceView content can't be captured into a hardware layer anyway.

### Cited Findings
- Overdraw = same pixel shaded multiple times per frame; "the most performance gains can be made by reducing full-screen layers"; low-end targets tolerate only ~2.5-3x average overdraw at 1080p60. — [Kodi skin optimizations](https://kodi.wiki/view/Skin_Optimizations); [bugnet: finding an overdraw bottleneck](https://bugnet.io/blog/how-to-fix-finding-an-overdraw-bottleneck-with-gpu-profiling)
- Mali GPUs are tile-based and use pixel-kill (Forward Pixel Kill / hidden-surface removal) that can eliminate occluded fragments "as good as front-to-back drawing order" — but only for opaque pixels; blended/transparent surfaces can't be killed. — [ARM: Killing Pixels — a new optimization for shading on Mali](https://developer.arm.com/community/arm-community-blogs/b/mobile-graphics-and-gaming-blog/posts/killing-pixels---a-new-optimization-for-shading-on-arm-mali-gpus)
- Official Android guidance: reduce overdraw by removing unnecessary backgrounds, flattening the view hierarchy, reducing transparency; set the window background to the app's main color and leave containers backgroundless; for full-screen opaque views set `android:windowBackground: @null`. — [Android: Reduce overdraw](https://developer.android.com/topic/performance/rendering/overdraw); [Android Developers Blog: window backgrounds & UI speed](https://android-developers.googleblog.com/2009/03/window-backgrounds-ui-speed.html)
- Hardware layers (`renderToHardwareTextureAndroid` maps to View layer-type hardware): rasterize the view into a GPU texture so animated opacity/scale/rotation composite on the RenderThread without redrawing — but "if you use hardware layers on a view that animates translateX or translateY with children that overflow its layout bounds, those children will be clipped to the view's bounds for the duration of the animation"; and hardware layers add overhead (render to layer, then layer to window). — [react-native-ease hardware-layers guide](https://www.mintlify.com/AppAndFlow/react-native-ease/features/hardware-layers); [Android Developers Blog: hardware acceleration](https://android-developers.googleblog.com/2011/03/android-30-hardware-acceleration.html)
- SurfaceView is composited by dedicated hardware separately from the app window (it is not drawn through the app's render pipeline), which is why it's power-cheaper than TextureView. — [Android 7.0 for Developers](https://developer.android.com/about/versions/nougat/android-7.0)

### Inferences
- `renderToHardwareTextureAndroid` on the sliding sides is a no: (a) translateX is the one case the hardware-layer guidance warns about; (b) a SurfaceView video wall can't be snapshotted into the layer — SurfaceView pixels live outside the app's drawing pass, so the "snapshot the hidden side into a texture" idea only works for the GL side if rendered via TextureView, and even then it re-rasterizes a full screen each time content changes. If a static snapshot of the hidden side is wanted during drag, a cheaper and fully controllable version is: capture once to an Image (e.g., GL readPixels/snapshot for the globe) and slide the Image — but react-freeze's retained native views already give the same effect for free.
- Overdraw hit-list for the transition window: opaque black background on each sibling root (no alpha), no app window background behind them (`windowBackground @null` or match), zero semi-transparent full-screen scrims/gradients during the drag (every blended full-screen layer costs a full extra screen of shading on Mali), and clip each sibling to its own screen-width bounds (`overflow: hidden` on the strip) so the GPU scissors out the offscreen portion.
- During the slide, total visible pixels across both siblings is exactly one screen (they don't overlap if laid side-by-side in a 2x-width strip). That means sliding per se doesn't double shaded pixels — doubling only happens if layers overlap or blend. The side-by-side strip layout is inherently overdraw-friendly; avoid the "stacked + opacity crossfade" alternative, which does blend two full screens.

### Gaps
- No Mali-specific published numbers for SurfaceFlinger composition cost when multiple SurfaceView layers move per frame (the video wall case); MediaTek clone HWCs may fall back to GPU composition (GLES) with many layers — verify with `dumpsys SurfaceFlinger` on-device.

## Q5. Deferring JS work so nothing re-renders during the ~300ms transition window

### Takeaway
There is no built-in RN mechanism that blocks re-renders during a Reanimated gesture; the working pattern is an app-level "transitioning" flag (shared value mirrored into a ref/store) that effects, stores, and list updates consult, plus InteractionManager/requestIdleCallback for post-settle scheduling. On new arch, RN deprecates InteractionManager in favor of requestIdleCallback.

### Cited Findings
- InteractionManager.runAfterInteractions schedules long-running work after interactions/animations complete; active touches count as an interaction and delay callbacks until all touches end; apps can register custom interaction handles (create on animation start, clear on completion) for manual control; deprecated in RN 0.81+ in favor of `requestIdleCallback`. — [RN 0.86 InteractionManager docs](https://reactnative.dev/docs/0.86/interactionmanager)
- Reanimated's own guidance keeps per-frame work on the UI thread and routes any required JS-side effect through `scheduleOnRN`, i.e., JS effects are explicitly out-of-band from the animation. — [tothenew Reanimated guide](https://www.tothenew.com/blog/?p=78074); [Reanimated performance guide](https://docs.swmansion.com/react-native-reanimated/docs/guides/performance)
- react-freeze: freezing a subtree suspends its renders while subscriptions keep running; renders resume with latest state on unfreeze — i.e., Freeze is itself a "don't re-render during this window" primitive with built-in catch-up semantics. — [react-freeze README](https://github.com/software-mansion/react-freeze)
- JS-thread work directly competes with gesture responsiveness only at the boundaries (gesture callbacks that hop to JS, shared-value reads from JS block the JS thread synchronously). — [Reanimated performance guide](https://docs.swmansion.com/react-native-reanimated/docs/guides/performance)

### Inferences
- Because the drag+settle runs entirely on the UI thread (Q2), JS-thread re-renders during the window cannot drop *gesture* frames by themselves — they hurt when they trigger Fabric commits/mutations on the UI thread mid-drag (view updates on the wall, feed item inserts). So the goal is narrower: suppress *commits into the two heavy subtrees* during the window.
- Concrete pattern: `transitioning` shared value set in `onStart` worklet; mirror to JS once via `scheduleOnRN(setFlagRef)` (a ref write, not a state set — no render). Feed/store subscriptions check the ref and buffer updates (queue new wall items, skip player source swaps); on settle (`onFinalize` -> `scheduleOnRN`), flush buffered updates inside `requestIdleCallback` (or InteractionManager on 0.86 where it still exists). `startTransition` is weaker here: it de-prioritizes renders but React can still commit during the window; the buffer-and-flush ref gate is deterministic.
- Freeze on the hidden side already halves the surface area of this problem: a frozen subtree can't commit no matter what the stores do.

### Gaps
- No source found documenting `startTransition`/concurrent-features behavior interacting with Reanimated gesture windows in RN new arch; treat startTransition as untested for this purpose.
- requestIdleCallback semantics on RN (Hermes) — whether it actually waits for interaction end like InteractionManager did — not confirmed by a primary source.

## Q6. Production evidence: pager internals and TikTok-like swipes between live surfaces

### Takeaway
Production pagers (ViewPager2 / react-native-pager-view) solve this with native-driven translation plus strict page retention limits; TikTok-style feeds universally converge on a 3-player pool (prev/current/next), visibility-gated playback, and recycling player instances without destroying decoder pipelines.

### Cited Findings
- react-native-pager-view wraps native ViewPager2 on Android (since v5); `offscreenPageLimit` (Android) sets how many pages are retained on each side of the visible page; limiting cached pages reduces memory and avoids rendering bottlenecks on low-resource devices. — [react-native-pager-view (GitHub mirror)](https://github.com/andreialecu/react-native-pager-view); [Expo SDK 57 PagerView docs](https://docs.expo.dev/versions/v57.0.0/sdk/ui/drop-in-replacements/pagerview.md); [Limit cached pages in ViewPager2](https://gurubase.io/g/android/limit-cached-pages-in-viewpager2)
- TikTok-style feed engines "only render 3 videos at a time (Previous, Current, Next)" and recycle players as you swipe; only the visible video plays, the rest pause; next one or two are preloaded so playback is instant. — [SwipeTok plugin writeup](https://forum.bubble.io/t/new-plugin-swipetok-free-pro-build-true-60fps-tiktok-reels-feeds-with-dom-virtualization-video-trimming/396624); [vp0: TikTok-style video feed](https://vp0.com/blogs/tiktok-style-video-feed-ui-template)
- Flutter's video_pool codifies the same: "a fixed pool of player instances, reusing them as the user scrolls — swapping video sources without destroying the decoder pipeline," combined with visibility tracking and disk caching for "smooth 60fps feeds on any device." — [video_pool (pub.dev)](https://pub.dev/documentation/video_pool/latest/)
- Mux published a 2025 guide to building a TikTok-style RN feed centered on preloading adjacent videos and careful player lifecycle management. — [Mux blog](https://www.mux.com/blog/slop-social)
- Staggering many players' work vs running them in-phase: frames over the 60Hz budget dropped from ~50% to <1% with 24 players (Unity/HAP — cross-stack principle). — [Bluecadet HAP performance](https://unity.bluecadet.com/hap/performance/)

### Inferences
- ViewPager2's model maps cleanly onto the two-sibling case: native-thread-driven translation of a side-by-side strip, both pages retained (`offscreenPageLimit=1` equivalent), content lifecycle (play/pause) driven by page-visibility callbacks AFTER the snap — not during the drag. Reanimated Pan + translateX on a 2x-width strip is the same architecture with full control.
- The TikTok lesson for the wall side: decoder count, not view count, is the budget on MediaTek clones. During the transition keep decoders untouched (pause after settle), and if wall tiles ever need per-tile players, pool them (N visible + 0 spare) rather than one per tile.

### Gaps
- Could not find a public engineering writeup from TikTok/Instagram on live-surface swipe internals (expected — proprietary); the closest public evidence is the pooling pattern repeated across SwipeTok, video_pool, and the Mux guide.

## Recommended recipe (synthesis)

1. Layout: 2x-screen-width strip, siblings side-by-side, `overflow:hidden`, opaque backgrounds, no window background behind them. No overlap = no blend = no extra Mali overdraw while sliding.
2. Drive: `Gesture.Pan()` -> shared value -> `useAnimatedStyle` translateX on the strip only. `withSpring` settle in `onEnd`. No runOnJS/measure/layout props/shared-value JS reads in the hot path. Memoize gesture + styles.
3. Enable `ANDROID_SYNCHRONOUSLY_UPDATE_UI_PROPS` (Reanimated feature flag) to skip the shadow-tree commit per frame.
4. Keep video on SurfaceView (`surfaceType='surface'`): translation is synchronous and artifact-free since Android 7; only switch to TextureView if the MediaTek HWC misbehaves on-device.
5. Gesture start does zero native work: incoming side shows retained pixels (react-freeze keeps native views); unfreeze via one deferred JS task; GL loop frame-skips via a boolean, players keep playing.
6. After settle only: freeze the hidden side, stop its GL rAF scheduling, pause its players (staggered if needed), flush buffered store updates via requestIdleCallback.
7. Gate commits: `transitioning` ref consulted by feed/store effects; buffer and flush, don't rely on startTransition.
8. Skip `renderToHardwareTextureAndroid` for the slide: wrong for translateX with full-bleed children, and can't capture SurfaceView pixels anyway.
