# Low-End Android Playbook: Degradation Without Looking Degraded + Jank Diagnostics

Scope: how major apps make media-heavy experiences feel fast on MediaTek-class SoCs / weak Mali GPUs / 4-6GB RAM, and device-side diagnostics that attribute jank correctly. Oriented toward a React Native live-video app, no platform fork.

## Key Question 1: Android Go / YouTube Go / Facebook Lite / Instagram Lite era techniques — what they cut, what they fake

### Takeaway
The Lite apps won on weak hardware by moving work off the device (server-side layout, server-resized images), capping client memory (image/resource caches in the tens of MB), and deleting whole classes of client work (animations, heavy UI interactions, GIFs). Google's own Android Go guidance is the same playbook at the platform level: trim on `onTrimMemory()`, branch on `isLowRamDevice()`/`getMemoryClass()`, and serve lower-resolution assets on constrained devices.

### Cited Findings
- Facebook Lite's architecture: a tiny client that is "a simple VM... and a rendering engine" while "product code is written on the server"; the server sends "screens to the client in the form of a compressed UI tree similar to a DOM," and only diffs are sent on minor screen changes — [Facebook Engineering: How we built Facebook Lite](https://engineering.fb.com/2016/03/09/android/how-we-built-facebook-lite-for-every-android-phone-and-network/)
- Facebook Lite image strategy: the Lite server (not a CDN) delivers "exact-size images over the same TCP connection," adjusting JPEG quality and formatting images "exactly at the size needed," chunking large images; a dedicated image server handles caching and transcoding — [Facebook Engineering](https://engineering.fb.com/2016/03/09/android/how-we-built-facebook-lite-for-every-android-phone-and-network/)
- Facebook Lite memory/perf budget: target device class was a 2009-era Samsung Galaxy Y (290 MB RAM, 600 MHz CPU); "cache sizes for images and resources are chosen to stay in the tens of MBs"; the client releases memory when backgrounded; "animations and other heavy UI interactions are avoided"; APK under 1 MB; custom protocol over TLS/TCP with LZMA2 (server→client) and DEFLATE (client→server) compression — [Facebook Engineering](https://engineering.fb.com/2016/03/09/android/how-we-built-facebook-lite-for-every-android-phone-and-network/); companion talk: [F8 2016: Facebook Lite — building for 2G connections and typical devices](https://developers.facebook.com/videos/f8-2016/facebook-lite-building-for-2g-connections-and-typical-devices/)
- Instagram Lite (2021, 170 countries) is under 2 MB and built on Bloks — server-defined logic rendered as native UI, shared across Instagram/Facebook/Messenger/WhatsApp — [TechCrunch](https://techcrunch.com/2021/03/10/facebook-targets-emerging-markets-with-instagram-lite-a-new-android-app-that-takes-up-just-2mb-in-170-countries)
- YouTube Go launched 2016 for low-end devices and slow connections; Google shut it down in August 2022, folding low-end optimizations into the main app — [Pocketnow: why lightweight Go/Lite apps are killed off](https://pocketnow.com/why-lightweight-go-lite-apps-are-killed-off)
- Android Go official memory guidance: use `onTrimMemory()` to release unneeded memory; use `ActivityManager.getMyMemoryState()` to find the current trim level; avoid concurrent memory-intensive operations (separate CPU-bound vs low-latency work into the right thread pools) — [Optimize memory for Android (Go edition)](https://developer.android.com/guide/topics/androidgo/optimize-memory)
- Android Go official guidance on media: "identify and optimize large or full-colored bitmaps"; avoid GIFs ("GIFs consume a lot of memory"); use WebP/pngcrush/pngquant for assets — [Android Go best practices](https://developer.android.com/guide/topics/androidgo/best-practices)
- Runtime capability branching: `ActivityManager.isLowRamDevice()` and `getMemoryClass()` tell you the device's memory constraints at runtime so you can "scale down your memory use — for example... use lower resolution images on low memory devices" — [Optimize for Android (Go edition)](https://developer.android.com/guide/topics/androidgo/optimize)

### Inferences
- The common thread is not "make everything faster," it's "decide centrally what the weak device never has to do": pre-size media server-side, cap caches with hard numbers, and delete animation classes outright rather than tuning them. For an RN live-video wall: serve wall-tile video/posters at exact tile resolution, cap the image cache in MB (not entries), and have a single `isLowRamDevice()`-style device-class gate that switches off springs/blur/shadows and shrinks list windows — mirroring what Tendbble does in RN (see Q1/Q6 cross-ref below).
- Server-driven UI (Bloks/Lite-style) is overkill for one app, but the cheap 80% is server-driven *asset* selection: the client declares its device class once and the backend returns smaller renditions and shorter feed pages.

### Gaps
- No public engineering deep-dive on YouTube Go's internals surfaced (only launch/shutdown coverage). Its documented tricks (preview-before-download, resolution picker with data cost shown) are known from product coverage, not engineering posts; I found no citable engineering source in this session.
- No Instagram Lite engineering-blog post with implementation detail was found — only launch press. Meta's Bloks posts exist but did not surface in results.

## Key Question 2: Perceived performance — what makes an interface FEEL instant (budgets, masking, optimistic UI)

### Takeaway
The authoritative numbers: ~100ms response-to-touch feels instantaneous (Nielsen 0.1s / Google RAIL R=100ms), ~1s keeps flow of thought, ~10s is the attention limit. Everything else is masking: skeletons instead of spinners, optimistic UI that renders the result before the server confirms, and showing *something* within 100ms even when the real work takes seconds.

### Cited Findings
- Nielsen's three limits: 0.1s = "the limit for having the user feel that the system is reacting instantaneously" (no feedback needed); 1.0s = limit for uninterrupted flow of thought (delay noticed, no feedback needed); 10s = limit for keeping attention on the dialogue, beyond which users task-switch and need completion feedback. Rooted in 1968 research (Miller), still the canonical budgets — [Jakob Nielsen, Time Scales of UX (UX Tigers)](https://www.uxtigers.com/post/time-scales-ux); [Nielsen substack version](https://jakobnielsenphd.substack.com/p/time-scale-ux)
- Google RAIL model (Response/Animation/Idle/Load): respond to user input in under 100ms — "users feel responses to their actions that happen in less than 100ms as immediate, and any longer the connection between action and reaction is broken"; for long-running operations, show a progress indicator or acknowledgement within that same 100ms — [web.dev: Measure performance with the RAIL model](https://web.dev/rail); secondary explainer: [A Faster Web: The RAIL performance model](https://www.afasterweb.com/2015/10/10/the-rail-performance-model/)
- Skeleton screens (solid-shape placeholders shown until content loads) are the standard pattern "everywhere in feeds on Instagram, LinkedIn, and YouTube" and visually outperform a blank screen + spinner by previewing the next screen and keeping the app interactive — [Diagram: Skeleton screens — giving body to your content](https://www.wearediagram.com/blog/skeleton-screens-giving-body-to-your-content); [UX Planet: Loading states UX patterns](https://uxplanet.org/loading-states-ux-patterns-9e8d2d45fa3c)
- Optimistic UI is "the single biggest lever for improving perceived performance": render the result of a like/add/toggle immediately, sync with the server afterwards — [DEV: The illusion of speed](https://dev.to/dct_technology/the-illusion-of-speed-ux-tricks-that-make-sites-feel-instant-3fp5)
- "Perceived latency is more important than actual latency — a 3-second operation that feels instant is better than a 1-second operation that feels slow"; a survey of faking-performance techniques (skeletons, progressive image reveal, animation to mask waits, preemptive loading) — [Stéphanie Walter: Lightning fast UX — faking performance when there's no code left to optimize](https://stephaniewalter.design/blog/lightning-fast-ux-faking-performance-when-theres-no-code-left-to-optimize/)
- Tendbble (RN/Expo video feed) bridges fast-scroll gaps with "thumbnail placeholders with blurhash encoding" until players initialize — placeholder-first rendering applied specifically to a video feed — [Expo blog: Shipping a performance-first video feed](https://expo.dev/blog/shipping-a-performance-first-video-feed-how-tendbble-built-a-real-time-social-app-with-expo)

### Inferences
- For the video wall: the contract per tile should be "within 100ms of entering the viewport, show *something* branded to that post" (blurhash/poster), with actual video attach allowed to take 400ms+ unnoticed. The user reads the blurhash→poster→first-frame sequence as *progress*, not as slowness — this is the core "illusionally fast" move, and it costs almost nothing on a weak GPU because blurhash is a tiny bitmap.
- RAIL's framing implies the touch-feedback path (press states, scroll start) must never share the JS thread with feed work in RN; anything over 100ms between gesture and visible reaction breaks the illusion regardless of average FPS.

### Gaps
- RAIL's per-frame animation budget (commonly quoted as 10ms/frame to leave compositor headroom at 60Hz) and the Load target did not appear verbatim in fetched material this session; confirm exact current numbers on web.dev/rail before quoting them in a report.
- No 2022+ peer-reviewed HCI study on mobile perceived-performance budgets surfaced; the field still cites Nielsen 1993/Miller 1968 thresholds.

## Key Question 3: MediaTek-specific pitfalls — codec counts, thermal, Mali/HWUI, little cores

### Takeaway
Hard MediaTek-specific public documentation is thin. What is well-documented: per-SoC concurrent codec limits live in vendor `media_codecs.xml` (`<Limit name="concurrent-instances" max="N"/>`), the media resource manager reclaims codecs by process priority, and on weak GPUs fill-rate (overdraw) is the documented bottleneck. Thermal evidence for Helio-class chips is anecdotal (the X20 throttled above ~33°C by dropping to its little-core cluster). Treat codec count, sustained clocks, and display refresh behavior as per-device unknowns to be measured, not assumed.

### Cited Findings
- Concurrent codec instance limits are declared per-codec in the vendor's `media_codecs.xml` via `<Limit name="concurrent-instances" max="N"/>`; example values in AOSP device trees run 6-16 for standard decoders with lower limits for secure decoders (e.g. 13 standard AVC / 4 secure AVC / 12 VP8 in one Google device config) — [AOSP crosshatch media_codecs.xml](https://android.googlesource.com/device/google/crosshatch/+/80d4375/media_codecs.xml); [AOSP redfin media_codecs.xml](https://android.googlesource.com/device/google/redfin/+/f2d0200/media_codecs.xml). These examples are Qualcomm devices; MediaTek values are in each device's own vendor files (readable on-device, see Q4 inference).
- The media resource manager's OEM-dependent behavior (which codecs count against which resources) is a documented AOSP integration point, i.e. explicitly vendor-specific — [AOSP: OEM dependencies of the media resource manager](https://source.android.com/devices/media/oem)
- `MediaCodec.CodecException` exposes `ERROR_INSUFFICIENT_RESOURCE` ("a required resource was not able to be allocated" — may be transient, retry later) and `ERROR_RECLAIMED` ("the resource manager reclaimed the media resource used by the codec" — codec is in terminal state and must be released) — [MediaCodec.CodecException reference](https://developer.android.com/reference/android/media/MediaCodec.CodecException)
- Resource reclaim follows process priority: higher-priority (foreground) processes reclaim codecs from lower-priority ones; "a background app should not be able to reclaim MediaCodec resources from a foreground app" — [AOSP CTS commit: MediaCodec resource management tests](https://android.googlesource.com/platform/cts/+/f9418364315%5E%21/)
- Helio X20 thermal behavior (anecdotal, 2015-16 era): the two A72 big cores were gated when the chip passed ~33°C, and under heat "the SoC would function like a Helio X10" (i.e. little-cluster-only); several OEMs reportedly dropped X20 projects over heat — [GSMArena newscomm thread](https://www.gsmarena.com/newscomm-16400p3.php); [PhoneArena leaked heat test](https://www.phonearena.com/news/MediaTek-Helio-X20-vs-Snapdragon-810-leaked-heat-test-results-show-a-clear-winner_id69411). Old and partly rumor-sourced — treat as a pattern illustration (big cores are the first thermal casualty), not as data about current Helio G/P chips.
- On weak GPUs the documented failure mode is fill-rate: "on less performant GPUs, available fill-rate... can be low," and as overdraw rises "the GPU might take longer to process new commands and ask the rest of the system to wait" — i.e. UI/RenderThread stall waiting on the GPU. Debug GPU Overdraw colors: blue=1x, green=2x, pink=3x, red=4x+ — [Reduce overdraw](https://developer.android.com/topic/performance/rendering/overdraw); [Debug GPU Overdraw tool](https://developer.android.com/tools/performance/debug-gpu-overdraw)
- Cheap-display gotcha: on some low-end devices the system runs the app at 30Hz vsync by default for power even though the panel is 60Hz; apps must explicitly request 60Hz (frame rate API) or they are silently half-rate — [bugnet.io: fix Android vsync throttled to 30Hz on cheap displays](https://bugnet.io/blog/fix-android-vsync-throttled-to-30hz-on-cheap-displays). Single independent blog source — verify on the actual clone phones by checking reported vsync period in Perfetto/gfxinfo.

### Inferences
- Clone phones add a layer of unreliability: a "fake S25" MediaTek clone may ship a `media_codecs.xml` copied or mis-tuned by the ROM vendor, so the *declared* concurrent-instances limit may exceed what the SoC actually sustains. The safe engineering posture is: treat `ERROR_INSUFFICIENT_RESOURCE` as an expected runtime signal, keep your own hard cap on simultaneous decoders (pool of 2-4), and degrade to posters when codec creation fails rather than crashing or retry-storming.
- Big.LITTLE implication of the X20 pattern generalized: under thermal pressure the scheduler loses big cores first, so JS-thread-heavy RN work (bridge traffic, list virtualization) degrades *before* the GPU does. Sustained-load testing (a soak loop) matters more than cold-start benchmarks on these chips.

### Gaps
- No public MediaTek developer documentation on Helio codec instance counts, HWUI tuning, or scheduler behavior surfaced; MediaTek's resources appear to be partner-NDA. Device-side inspection (reading `/vendor/etc/media_codecs*.xml` via adb, `MediaCodecList`/`CodecCapabilities.getMaxSupportedInstances()`) is the only reliable route — this is an API-level fact I did not fetch a page for; verify against the MediaCodecInfo.CodecCapabilities reference before citing.
- No measured thermal-throttling curves for modern Helio G-series under video load were found (reviews like [Digit's Realme 7 / Helio G95 review](https://www.digit.in/features/mobile-phones/realme-7-performance-review-can-the-mediatek-helio-g95-make-a-difference-56183.html) exist but were not fetched for specifics).
- No Mali-specific (vs Adreno) HWUI quirk documentation found beyond the generic fill-rate/overdraw guidance.

## Key Question 4: Diagnostics — telling JS-thread vs UI-thread vs RenderThread vs GPU jank apart without root

### Takeaway
`dumpsys gfxinfo <pkg> framestats` gives per-frame nanosecond timestamps for every pipeline stage and `reset` makes it scriptable in an adb loop; Perfetto/Studio's jank detection separates UI thread (`Choreographer#doFrame`), RenderThread (`DrawFrames`), and GPU completion. For RN, "JS-thread jank" is invisible to gfxinfo (frames simply don't get scheduled) — you detect it as *absence* of frames plus a saturated JS thread in a Perfetto trace, vs UI/RenderThread jank which shows up as slow stages inside framestats.

### Cited Findings
- `adb shell dumpsys gfxinfo <PACKAGE_NAME> framestats` prints per-frame nanosecond timestamps with columns: FLAGS, INTENDED_VSYNC, VSYNC, OLDEST_INPUT_EVENT, NEWEST_INPUT_EVENT, HANDLE_INPUT_START, ANIMATION_START, PERFORM_TRAVERSALS_START, DRAW_START, SYNC_QUEUED, SYNC_START, ISSUE_DRAW_COMMANDS_START, SWAP_BUFFERS, FRAME_COMPLETED. FLAGS=0 means a valid frame for timing analysis — [Android testing/performance doc (archived official copy)](https://iut-fbleau.fr/docs/android/training/testing/performance.html)
- Phase math from those columns: total frame time = FRAME_COMPLETED − INTENDED_VSYNC; input handling = ANIMATION_START − HANDLE_INPUT_START; layout/measure ends at DRAW_START; UI-thread draw = SYNC_START − DRAW_START; everything after ISSUE_DRAW_COMMANDS_START through SWAP_BUFFERS→FRAME_COMPLETED is RenderThread/GPU side — [archived official doc](https://iut-fbleau.fr/docs/android/training/testing/performance.html)
- `adb shell dumpsys gfxinfo <PACKAGE_NAME> reset` clears the counters so a script can measure a clean window per scenario; since Android 6.0 the plain `dumpsys gfxinfo` aggregate includes total/janky frame counts, 90/95/99th percentile frame times, missed-vsync count, high input latency, slow UI thread, slow bitmap uploads, slow draw counts — [archived official doc](https://iut-fbleau.fr/docs/android/training/testing/performance.html)
- Studio/Perfetto jank workflow: the Display "Frames" track marks janky frames red; the relevant threads are UI thread, RenderThread, and GPU completion. `Choreographer#doFrame` = UI thread work (input/animation/layout/draw); `DrawFrames` = RenderThread issuing GPU commands; long main-thread trace events identify the blocking component. Complex cases: export the trace into the Perfetto web UI for SQL queries — [Android Studio: UI jank detection](https://developer.android.com/studio/profile/jank-detection)
- Jetpack Macrobenchmark wraps this as `FrameTimingGfxInfoMetric` (frame timing collected via `dumpsys gfxinfo`), confirming gfxinfo as the sanctioned no-root automation surface — [androidx.benchmark.macro.FrameTimingGfxInfoMetric](https://developer.android.com/reference/kotlin/androidx/benchmark/macro/FrameTimingGfxInfoMetric)
- Practitioner guides for automating jank tests on top of gfxinfo/JankStats exist, e.g. [@JankTest deep dive (ProAndroidDev)](https://proandroiddev.com/deep-dive-into-writing-performance-tests-with-janktest-46494e46b43) and [Demystifying Android rendering (ashishb)](https://ashishb.net/programming/demystifying-android-rendering/)
- HWUI's own JankTracker categorizes jank causes but has a known limitation attributing RenderThread-caused jank (TODO in source) — [AOSP JankTracker.cpp](https://android.googlesource.com/platform/frameworks/base/+/e927ec0/libs/hwui/JankTracker.cpp)

### Inferences
- Decision tree for a no-root adb loop on the clone phones: (1) `reset`, run scenario, dump aggregate → if janky% high, pull framestats; (2) DRAW_START−PERFORM_TRAVERSALS_START big → layout/measure (RN view tree too deep / too many tiles mounting); (3) SYNC_START−DRAW_START or SYNC delay big → UI thread draw / bitmap uploads (oversized images); (4) SWAP_BUFFERS−ISSUE_DRAW_COMMANDS_START big → RenderThread/GPU-bound (overdraw, too many video layers — cross-check with Debug GPU Overdraw colors); (5) frames *missing* entirely (low frame count while scrolling) with low per-frame times → JS thread starved: confirm with a Perfetto trace showing the `mqt_js` thread pegged. gfxinfo alone cannot see RN's JS thread; combine both.
- `INTENDED_VSYNC` deltas also reveal the actual vsync period the app is being served — the cheap-display 30Hz throttle from Q3 is directly detectable in framestats without any extra tooling.

### Gaps
- The live developer.android.com URL for the framestats column documentation 404'd (content moved); the archived mirror above matches the original official text, but the current canonical URL should be located before publishing (likely under the Macrobenchmark/"slow rendering" docs).
- No source found describing RN-specific jank attribution (JS vs UI thread) as an official documented workflow; the decision tree above is inference from how RN schedules frames.

## Key Question 5: Memory pressure on 4-6GB devices — decoder allocation, GC, staying under thresholds

### Takeaway
On 4-6GB devices the enemy chain is: background pressure → lmkd kills caches/processes and the media resource manager reclaims codecs → your decoder allocation fails (`ERROR_INSUFFICIENT_RESOURCE`) or your process gets reclaimed. Defenses with documented backing: respond to `onTrimMemory()`, keep image caches hard-capped in MB, purge in priority order (video buffers → decoded images → data caches), and never hold more decoders than visible tiles need.

### Cited Findings
- lmkd monitors system memory and "reacts to high memory pressure by killing the least essential processes"; Android 11+ uses PSI (pressure stall information) with thrashing detection; kill strategies explicitly differ by device class — low-memory devices must "tolerate higher memory pressure as a normal mode of operation" — [AOSP: Low memory killer daemon](https://source.android.com/docs/core/perf/lmkd)
- Codec reclaim under pressure/priority is a first-class mechanism: `ERROR_RECLAIMED` (codec taken, release it) and `ERROR_INSUFFICIENT_RESOURCE` (allocation failed, possibly transient, retry later) — [MediaCodec.CodecException](https://developer.android.com/reference/android/media/MediaCodec.CodecException); reclaim priority favors foreground over background processes — [AOSP CTS commit](https://android.googlesource.com/platform/cts/+/f9418364315%5E%21/)
- `onTrimMemory()` + `ActivityManager.getMyMemoryState()` is the official hook for shedding caches at the right pressure level; avoid parallel memory-intensive tasks — [Android Go: optimize memory](https://developer.android.com/guide/topics/androidgo/optimize-memory)
- Facebook Lite's hard numbers: image/resource caches "chosen to stay in the tens of MBs" and memory released when backgrounded — [Facebook Engineering](https://engineering.fb.com/2016/03/09/android/how-we-built-facebook-lite-for-every-android-phone-and-network/)
- Tendbble's RN implementation of the same idea: backgrounding triggers proactive cache cleanup; a "priority-based purge system: video buffers clear first, then image decode caches, then query caches"; expo-image's decoded bitmap cache is flushed periodically during long scroll sessions to prevent accumulation — [Expo blog: Tendbble video feed](https://expo.dev/blog/shipping-a-performance-first-video-feed-how-tendbble-built-a-real-time-social-app-with-expo)
- Tendbble's single-active-player rule "cuts peak memory usage in half" versus mounting players per visible card; they reduced active subscriptions from 20-30 to 3-4 — [Expo blog](https://expo.dev/blog/shipping-a-performance-first-video-feed-how-tendbble-built-a-real-time-social-app-with-expo)
- react-native-video official performance guidance: pool of 3-5 reusable players for feeds; `initializeOnCreation: false` for off-screen videos (lazy player creation); playing multiple videos at once causes "overlapping audio and memory spikes"; not recycling players "leak[s] memory until the app crashes" — [react-native-video performance docs](https://www.mintlify.com/TheWidlarzGroup/react-native-video/advanced/performance)
- Scale image memory by device: `isLowRamDevice()`/`getMemoryClass()` → lower-resolution images on low-memory devices; avoid GIFs entirely — [Android Go optimize](https://developer.android.com/guide/topics/androidgo/optimize); [best practices](https://developer.android.com/guide/topics/androidgo/best-practices)

### Inferences
- A 4-6GB clone phone with a bloaty ROM behaves like a Go-edition device under load: assume codec allocation can fail at any time and make poster-fallback the designed path, not an error path. The app's own decoder cap should sit well below the vendor-declared concurrent-instances limit, because other apps and the ROM's own services compete for the same codec pool.
- Player buffer sizing is a memory lever the RN layer controls (ExoPlayer `LoadControl` via react-native-video props): shorter back-buffers and smaller max buffers trade rebuffer risk for survival under lmkd pressure. No fetched source quantified ideal values — measure on-device.

### Gaps
- No public source quantifying lmkd kill thresholds specifically on 4-6GB MediaTek ROMs (these are vendor-tunable properties); read them off the device (`getprop | grep lmk`, `/proc/pressure/memory`) rather than citing generic numbers.
- No authoritative source found tying Java GC pause behavior under memory pressure to decoder starvation specifically; the connection (heap pressure → GC churn → dropped frames) is standard but was not documented in fetched sources.

## Key Question 6: Frame-rate strategy on weak GPUs — stable 30/45 vs unstable 60, per-surface rates

### Takeaway
Android 11+ has a real per-surface frame-rate API (`Surface.setFrameRate` / `SurfaceControl.Transaction.setFrameRate`), designed exactly for "this video surface is 30fps, the rest of the UI is 60": each surface declares its own rate and the platform reconciles (possibly running the display at a common multiple). Video surfaces should declare `FRAME_RATE_COMPATIBILITY_FIXED_SOURCE` with the exact content rate. Separately, production RN feed apps do adapt per device class — smaller list windows and simpler animations on low-end Android to hold a stable rate rather than chase 60.

### Cited Findings
- The frame rate API (Android 11 / API 30+) has four variants: `Surface.setFrameRate()`, `SurfaceControl.Transaction.setFrameRate()`, `ANativeWindow_setFrameRate()`, `ASurfaceTransaction_setFrameRate()` — [Android frame rate guide](https://developer.android.com/media/optimize/performance/frame-rate)
- Video surfaces pass the exact content rate (e.g. 29.97, not 30) with `FRAME_RATE_COMPATIBILITY_FIXED_SOURCE`; non-video surfaces use `FRAME_RATE_COMPATIBILITY_DEFAULT`. `CHANGE_FRAME_RATE_ONLY_IF_SEAMLESS` (default) vs `CHANGE_FRAME_RATE_ALWAYS` (allows a visible mode switch; recommended only for long-form playback, with a ~2s stabilization wait after `onDisplayChanged`) — [Android frame rate guide](https://developer.android.com/media/optimize/performance/frame-rate)
- Per-surface reconciliation is explicit: "Each surface can independently call setFrameRate() with its intended rate... the platform may optimize to a common multiple (e.g. run at 120Hz to satisfy both 60Hz and 24Hz surfaces)"; when running at a multiple, set presentation timestamps to avoid judder — [Android frame rate guide](https://developer.android.com/media/optimize/performance/frame-rate)
- Hygiene rules: call `setFrameRate()` once per content change (not per frame); call `setFrameRate(0)` when the surface stops submitting frames; never assume the platform honored the request — [Android frame rate guide](https://developer.android.com/media/optimize/performance/frame-rate)
- Low-end counter-gotcha: some cheap devices default apps to 30Hz for power even on 60Hz panels; the app must request 60Hz to get it — [bugnet.io](https://bugnet.io/blog/fix-android-vsync-throttled-to-30hz-on-cheap-displays) (single blog source; verify on-device)
- Production per-device-class adaptation in RN: Tendbble uses "adaptive window sizing based on device capability" — big windows at 120fps on ProMotion iOS, "reduced list windows" on lower-end Android "to maintain 60fps stability"; spring-physics animations are disabled entirely on low-end Android in favor of simple easing curves and increased gesture-throttle intervals — [Expo blog: Tendbble](https://expo.dev/blog/shipping-a-performance-first-video-feed-how-tendbble-built-a-real-time-social-app-with-expo)
- List-layer frame-rate reality on low-end Android: FlashList benchmarks claim up to 5x UI-thread FPS and 10x JS-thread FPS over FlatList on low-end Android — cited in [react-native-video performance docs](https://www.mintlify.com/TheWidlarzGroup/react-native-video/advanced/performance) (originates from Shopify's FlashList benchmarks; verify against Shopify's published numbers before quoting)
- Pinterest published an Android video optimization write-up ("Pinterest: turbocharge Android video with these simple steps") — [The New Stack](https://thenewstack.io/pinterest-turbocharge-android-video-with-these-simple-steps/) (not fetched in this session; flagged as a promising primary-adjacent source for a follow-up)

### Inferences
- For the void's live wall: declare each wall-tile video surface at its true content rate via `setFrameRate(fps, FIXED_SOURCE, ONLY_IF_SEAMLESS)` (ExoPlayer does this automatically for its own surface in recent versions — verify the react-native-video/ExoPlayer version in use actually calls it), and keep UI chrome at default. On a 60Hz-only Mali panel there is no seamless switch available, so the realistic strategy is not display-mode switching but *content pacing*: run tile videos at 24/30fps source rate (half the vsyncs idle), and cap your own JS-driven animations to cheap transforms. A stable 30fps video inside a 60Hz UI looks intentional; a 60fps target that oscillates 35-60 looks broken — this matches the Tendbble choice of stability over peak rate, though no fetched source states the 30-stable-beats-60-unstable rule verbatim.
- The degradation ladder that follows from all sources combined: (device-class gate) → smaller render window + fewer mounted tiles → posters-first with blurhash → single/dual active decoder → simpler easing, no springs → exact-size images with MB-capped cache → `onTrimMemory` purge ladder. Each rung is invisible individually; the sum is the "degraded without looking degraded" experience.

### Gaps
- No public source confirming whether major apps (YouTube, Instagram, TikTok) selectively call `setFrameRate()` per surface on low-end devices — their binaries aren't documented. The API doc's design intent (video vs UI surfaces) is the best available evidence.
- No fetched source quantifying Mali-class GPU headroom at 30 vs 60fps compositing for multi-video layouts; this needs on-device measurement (framestats SWAP_BUFFERS deltas at both rates).
