# Budget decoders, gate frames, freeze late

All three symptoms — scroll jank on the live wall, the globe's untextured first render, and the laggy translateX swap — are contention over the same three scarce resources on a low-end MediaTek clone: **hardware video decoder instances, the Android main (UI) thread, and Mali GPU fill/composition bandwidth**. The highest-leverage fixes are allocation policy, not tuning. Three changes are safe by construction and should be applied first: (1) a **fixed pool of expo-video players** created at idle — never per-tile, never during scroll — with small buffers and a pause-don't-release scroll discipline, because expo-video constructs and releases ExoPlayer on the main thread ([expo-video VideoPlayer.kt](https://github.com/expo/expo/blob/main/packages/expo-video/android/src/main/java/expo/modules/video/player/VideoPlayer.kt)); (2) **preloading the globe texture and gating the first `gl.endFrameEXP()`** behind a warm-up render, which makes an untextured first paint structurally impossible because the TextureView presents nothing until that call ([Expo GLView docs](https://docs.expo.dev/versions/v57.0.0/sdk/gl-view.md)); (3) the surface swap as a **2×-screen-width strip driven by a Pan-gesture worklet writing one shared value**, with nothing paused, frozen, or unmounted until after the spring settles — the whole gesture lifecycle then never touches the JS thread ([Reanimated performance guide](https://docs.swmansion.com/react-native-reanimated/docs/guides/performance)). Behind these sit measurement-gated changes — TextureView tiles, the `ANDROID_SYNCHRONOUSLY_UPDATE_UI_PROPS` flag, react-freeze, rendition capping, pool size — each decided by a cheap on-device check (gfxinfo framestats, `dumpsys SurfaceFlinger`, logcat decoder names) rather than by faith.

## The prioritized intervention list

Apply top-down. "Safe" means the mechanism guarantees the outcome or the change is trivially reversible with no new failure mode; "Gated" means an on-device measurement decides whether to keep it (the gate is named in the relevant section).

| # | Intervention | Symptom | Expected effect | Risk | Status |
|---|---|---|---|---|---|
| 1 | Fixed player pool (created at idle, one per frame); tiles acquire/`replace()` sources; never `useVideoPlayer` per tile | Scroll jank | Removes main-thread ExoPlayer create/release from the scroll path — the single biggest jank source | Low; pool plumbing only | Safe (pool **size** is gated) |
| 2 | Scroll policy: pause on fling, keep surfaces attached, source-swap one per frame at scroll-end; release only at true idle | Scroll jank | Flat main-thread load during fling; no decoder churn | Low | Safe |
| 3 | `bufferOptions ≈ {preferredForwardBufferDuration: 4, minBufferForPlayback: 1, maxBufferBytes: 8MB}` vs 20 s default | Scroll jank, memory | Cuts per-tile buffer memory ~4-5×; keeps live tiles near live edge | Slightly more rebuffer risk | Safe |
| 4 | Tiles get the low-rendition HLS **media** playlist URL directly (no master/ABR); fullscreen gets master | Scroll jank, decoder budget | Lower decode throughput per tile; raises usable concurrent-instance count | Low; URL-level change | Safe |
| 5 | Preload earth texture (`Asset.loadAsync` before mount) + warm-up render + gate first `endFrameEXP()` | Globe first render | Untextured first paint eliminated by construction | None | Safe |
| 6 | On-demand globe render loop (render only during pan/decay/invalidate); opaque GLView | Globe cost, swap lag | Idle globe = zero GPU cost ceded to video decoders | None | Safe |
| 7 | Pan gesture → shared value → `translateX` on one strip; `withSpring` settle in `onEnd`; no `runOnJS`/`measure()`/JS shared-value reads in hot path; memoized gesture + styles | Swap lag | Gesture never touches JS thread; two animated views ≪ the 100-component low-end budget | None | Safe |
| 8 | Do **nothing** at gesture start; pause hidden side's players + stop its GL rAF only **after** settle, staggered | Swap lag | No native work lands on the gesture frame | None | Safe |
| 9 | `transitioning` ref gate: stores buffer feed updates during drag, flush via `requestIdleCallback` after settle | Swap lag | No Fabric commits into the heavy subtrees mid-drag | Low | Safe |
| 10 | Tile view hygiene: one host view/tile, transforms not top/left, no state updates during scroll, memoized tiles, pause off-screen loaders via `animationPlayState: 'paused'` | Scroll jank | Fewer host views, fewer commits, fewer per-frame animators on the main thread | Low | Safe |
| 11 | `surfaceType="textureView"` for wall tiles; `surfaceView` for fullscreen player | Scroll jank, swap lag | Avoids HWC overlay-plane overflow → GPU client composition | TextureView costs one GPU copy per tile | **Gated** (dumpsys SurfaceFlinger) |
| 12 | Reanimated flag `ANDROID_SYNCHRONOUSLY_UPDATE_UI_PROPS` | Swap lag | Skips per-frame shadow-tree commit; −11 % measured on a Moto G8 Plus | Opt-in flag, "potential visual bugs" | **Gated** (visual QA + framestats) |
| 13 | react-freeze on the fully hidden side, flipped post-settle | Swap lag, steady-state | Hidden subtree cannot commit at all | Fabric stale-content report (single-sourced); placeholder-null layout collapse if misused | **Gated** (on-device unfreeze check) |
| 14 | Replace per-tile `expo-linear-gradient` views with `experimental_backgroundImage` (or one wall-wide underlay); kill blended full-screen scrims during the drag | Scroll jank, swap lag | Removes a whole overdraw layer per tile on a fill-rate-bound Mali | `experimental_` prefix | **Gated** (Debug GPU overdraw) |

## Scroll jank: decoder count is the budget, and player churn is the spike

Every production feed that works on weak hardware converges on the same architecture: a small fixed pool of pre-built players, recycled rather than destroyed. Reddit sizes its pool at **(prefetch × 2) + 2** and returns a recycled ViewHolder's player to the pool "instead of being destroyed," with prewarming (prepare + first-segment decode before visibility) yielding **+19 % of videos starting under 250 ms** ([Reddit's ExoPlayer techniques](https://proandroiddev.com/taking-exoplayer-further-reddits-performance-techniques-f426fdafb471)). Pinterest pools players keyed by codec format to avoid decoder re-init on recycle ([Pinterest via The New Stack](https://thenewstack.io/pinterest-turbocharge-android-video-with-these-simple-steps/)) — moot for the wall if the HLS ladder is normalized to one codec, which it should be. Tendbble's single-active-player discipline "cuts peak memory usage in half" ([Expo blog: Tendbble](https://expo.dev/blog/shipping-a-performance-first-video-feed-how-tendbble-built-a-real-time-social-app-with-expo)). Critically, none of these apps genuinely play 6-10 decoders at once; they run 1-3 playing plus prewarmed idle players. If the wall shows more tiles than the pool holds, overflow tiles keep posters/blurhash and live slots rotate — a blurhash within 100 ms reads as progress, not slowness, per the RAIL/Nielsen 100 ms instantaneity budget ([web.dev RAIL](https://web.dev/rail); [Nielsen time scales](https://www.uxtigers.com/post/time-scales-ux)).

The reason pooling specifically kills *scroll* jank is thread placement: expo-video builds ExoPlayer with `setLooper(context.mainLooper)` and runs `release()` on the main dispatcher ([expo-video VideoPlayer.kt](https://github.com/expo/expo/blob/main/packages/expo-video/android/src/main/java/expo/modules/video/player/VideoPlayer.kt)) — every mid-scroll create or release is a direct main-thread stall in the same frame budget the scroll needs. Hence intervention 2: pause (cheap) on fling, keep surfaces attached, defer source `replace()` to scroll-end and spread swaps one per frame. The staggering principle has cross-stack evidence: with 24 simultaneous players, phase-staggering player work dropped frames over the 60 Hz budget from **~50 % to under 1 %** ([Bluecadet HAP performance](https://unity.bluecadet.com/hap/performance/)).

Decoder exhaustion on these clones is silent, not loud. expo-video enables `setEnableDecoderFallback(true)`, so when the hardware decoder pool is exceeded, ExoPlayer falls back to software `c2.android.*` decoders on the CPU — thermal throttle follows, and MediaTek's big cores are historically the first thermal casualty, which starves the JS thread before the GPU degrades ([expo-video VideoPlayer.kt](https://github.com/expo/expo/blob/main/packages/expo-video/android/src/main/java/expo/modules/video/player/VideoPlayer.kt)). The vendor-declared limit lives in `media_codecs.xml` as `<Limit name="concurrent-instances" max="N"/>` ([AOSP OEM media docs](https://source.android.com/docs/core/media/oem)), but counterfeit firmware may declare wrong values, so the pool size is **measurement-gated**: dump `/vendor/etc/media_codecs*.xml` from both phones, then ramp players up empirically until logcat shows `DecoderInitializationException` or tiles decoding on `c2.android.*`/`OMX.google.*` instead of MediaTek hardware decoders — that string check is the cheapest runtime detector. Expect `ERROR_INSUFFICIENT_RESOURCE` (transient, retry) and `ERROR_RECLAIMED` (terminal, release) as designed-for runtime signals with poster fallback, not error states ([MediaCodec.CodecException](https://developer.android.com/reference/android/media/MediaCodec.CodecException); [Bitmovin single-decoder limitations](https://developer.bitmovin.com/playback/docs/understanding-single-decoder-device-limitations)). Note that `muted` only sets volume to 0 — the audio decoder keeps running per tile; truly freeing it needs the `setTrackTypeDisabled(C.TRACK_TYPE_AUDIO)` native patch or a video-only rendition server-side ([media3 track selection](https://developer.android.com/media/media3/exoplayer/track-selection)).

On the view side, the Fabric mount phase (host view creation/update on the Android main thread) is the expensive step, and the levers are fewer host views and fewer commits: don't defeat view flattening with styled wrapper views ([RN view flattening](https://reactnative.dev/architecture/view-flattening)), move tiles with transforms rather than top/left so no Yoga layout runs per change, and make zero state updates during active scroll (defer to momentum-end; `InteractionManager` is deprecated in favor of `requestIdleCallback` ([RN 0.86 InteractionManager](https://reactnative.dev/docs/0.86/interactionmanager))). Dozens of infinite Reanimated CSS loaders are dozens of per-frame property writes on the same main thread that handles scroll — pause off-screen ones with `animationPlayState: 'paused'` ([Reanimated docs](https://docs.swmansion.com/react-native-reanimated/docs/css-animations/animation-play-state)); if loader count can't drop, the documented scalable shape is a single Skia `Atlas` canvas — one GPU draw call for N sprites ([react-native-skia Atlas](https://www.mintlify.com/shopify/react-native-skia/shapes/atlas)). Two warnings for the current absolute-positioned-tiles-in-ScrollView layout: `removeClippedSubviews` is explicitly buggy with absolute positioning and saves no memory anyway ([RN optimizing-flatlist 0.86](https://reactnative.dev/docs/0.86/optimizing-flatlist-configuration)), so off-screen tile bounding must be manual windowing (mount only ±1.5-2 viewports) or a move to FlashList v2's new-arch recycling ([Shopify FlashList v2](https://shopify.engineering/flashlist-v2)); and per-tile `expo-linear-gradient` views are stacked blended layers that defeat Mali's pixel-kill, which only culls **opaque** pixels ([ARM: Killing Pixels](https://developer.arm.com/community/arm-community-blogs/b/mobile-graphics-and-gaming-blog/posts/killing-pixels---a-new-optimization-for-shading-on-arm-mali-gpus)) — gate the `experimental_backgroundImage` swap on Android's Debug GPU Overdraw colors ([Android overdraw guide](https://developer.android.com/topic/performance/rendering/overdraw)).

The TextureView-vs-SurfaceView call for tiles is the one genuinely two-sided decision. SurfaceView is cheaper per instance (dedicated hardware composition, fewer copies, lower power) ([media3 surface docs](https://developer.android.com/media/media3/ui/surface)), but each SurfaceView demands a hardware-composer overlay plane, and 6-10 planes likely overflow a low-end SoC's HWC into GPU client composition — potentially costing more than TextureView's one-copy-per-tile inside the normal view hierarchy. expo-video's `surfaceType` is create-time-only ([Expo video docs](https://docs.expo.dev/versions/latest/sdk/video/)). **Gate**: run the wall both ways and check `adb shell dumpsys SurfaceFlinger` for "Client composition" plus framestats SWAP_BUFFERS deltas; keep SurfaceView for the single fullscreen player either way.

## Gate the first endFrameEXP and the globe cannot render untextured

The incomplete first render has a mechanical cause and a mechanical fix. expo-gl presents nothing until the first `gl.endFrameEXP()` — it is the explicit "swap buffers" call ([Expo GLView docs](https://docs.expo.dev/versions/v57.0.0/sdk/gl-view.md)) — while expo-three's `new TextureLoader().load()` returns a texture that is "immediately ready but it'll load asynchronously," which is precisely the untextured-sphere pop-in ([expo-three README](https://github.com/expo/expo-three)). The fix sequence: `Asset.loadAsync(require('earth.jpg'))` at app start, before the globe screen mounts; in `onContextCreate`, `await ExpoTHREE.loadAsync(asset)` (fast — the file is already local, and expo-gl's `texImage2D` decodes the `{ localUri }` natively, off the JS thread); force the GPU upload with one warm-up render (GPU vendors explicitly recommend init-time upload plus a warm-up draw to "avoid the cost and potential stutters when they are uploaded on first use" ([Imagination texture guidance](https://docs.imgtec.com/performance-guides/performance-recommendations/html/topics/texture-uploading.html))); only then call the first `endFrameEXP()`. The first visible frame is fully textured **by construction** — this is the zero-risk, apply-today item. Preloading also dodges a second trap: the `onContextCreate` handler runs on the JS thread, so a feed-busy JS thread delays texture load exactly when the globe first mounts.

Don't spend effort on compressed textures: `compressedTexImage2D()` is in expo-gl's documented list of unimplemented methods, so KTX2/Basis/ETC2 is a dead end on this stack regardless of three.js loader support ([Expo GLView docs](https://docs.expo.dev/versions/v57.0.0/sdk/gl-view.md)). The practical equivalents are a smaller source (1024×512 is plausibly indistinguishable at phone globe sizes — gated on visual check), mipmaps (bandwidth, cache efficiency, and quality all improve on mobile GPUs ([Android AGI texture bandwidth](https://developer.android.com/agi/sys-trace/texture-memory-bw?hl=en))), and no alpha channel.

Steady-state, the globe's cheapest contribution to the whole system is to not render: three.js's own guidance is render-on-demand — once at start, then only on change, with damping re-rendering until motion rests ([three.js: rendering on demand](https://threejs.org/manual/en/rendering-on-demand.html)). Render only while a pan is active, while `withDecay` still moves the shared value beyond an epsilon, or on explicit invalidate; an idle globe then costs zero GPU while the video wall decodes, and because expo-gl Android has real per-frame overhead anyway (a 100-cube scene ran ~26 fps where a WebView was smooth ([Expo forums](https://forums.expo.dev/t/expo-gl-really-poor-performance-how-to-improve/46540))), frames not rendered are the biggest win available. Drive rotation from `Gesture.Pan` worklets writing shared values (UI-thread input sampling), read in the JS rAF loop — never PanResponder, which adds JS-thread queuing latency — and run momentum as `withDecay` on the shared value so the globe catches up after a dropped JS frame instead of accumulating stale events. Skip MSAA chasing: expo-gl's `msaaSamples` is iOS-only and mipmapped filtering handles the sphere interior ([Expo GLView docs](https://docs.expo.dev/versions/v57.0.0/sdk/gl-view.md)). The raw-GL-in-worklet rewrite (three.js is explicitly unsupported in the worklet context) is the escalation path only if JS-thread stalls remain visible after the wall fixes land — it is experimental API plus a partial rewrite.

## The swap: one translated strip, zero JS, and nothing pauses until settle

The transition's correct shape is a 2×-screen-width strip, siblings side-by-side, `overflow: hidden`, opaque backgrounds, with `transform: [{translateX}]` animated on **the strip only** — never per-tile. Side-by-side means total visible pixels during the drag is exactly one screen; sliding doubles shaded pixels only if layers overlap or blend, so the strip layout is inherently overdraw-friendly where a stacked-crossfade is not. Two animated views sit far inside Reanimated's "no more than 100 components on low-end Android" budget, and the measured curve shows why discipline matters: **7.25 ms per frame at 10 animated views, 11.98 ms at 100** on a Moto G8 Plus — the 16.67 ms budget dies well before 500 ([Expo animations benchmark](https://expo.dev/blog/the-real-cost-of-react-native-animations-benchmarking-every-approach)). The contract-breaker checklist for the drag window: no `runOnJS` in `onUpdate`, no `measure()` (screen width is known), no reading the progress shared value from JS (it synchronously blocks the JS thread ([Reanimated performance guide](https://docs.swmansion.com/react-native-reanimated/docs/guides/performance))), no React state sets in gesture callbacks, and gesture + animated styles memoized so parent re-renders don't recreate them. Settle with `withSpring` started inside the `onEnd` worklet; the single JS hop is one deferred "active side changed" notification after settle.

Even a pure-transform animation commits through the shadow tree per frame on the new architecture (Yoga pass, prop diff, mutation); the `ANDROID_SYNCHRONOUSLY_UPDATE_UI_PROPS` feature flag short-circuits this by pushing visual props directly to the UI layer — measured at **11.87 ms → 10.57 ms (−11 %)** at 50 views ([Expo animations benchmark](https://expo.dev/blog/the-real-cost-of-react-native-animations-benchmarking-every-approach)) — but it is opt-in "due to potential visual bugs," so it is measurement-gated: enable, run visual QA on both clones, keep if framestats improve and nothing glitches ([Reanimated performance guide](https://docs.swmansion.com/react-native-reanimated/docs/guides/performance)).

Translation itself is not the hazard it is reputed to be. Since Android 7.0, SurfaceView window position updates synchronously with View rendering — translating and scaling causes no artifacts ([Android 7.0 release notes](https://developer.android.com/about/versions/nougat/android-7.0)); react-native-video's "SurfaceView cannot be animated" wording is legacy-conservative. Black flashes come from attach/detach and surface recreation, not movement — so both siblings stay mounted across the swap, always, with an opaque backing view behind each player. `renderToHardwareTextureAndroid` is explicitly wrong here twice over: hardware layers clip children that overflow bounds during translateX animations, and SurfaceView pixels live outside the app's drawing pass and cannot be captured into a layer ([hardware-layers guide](https://www.mintlify.com/AppAndFlow/react-native-ease/features/hardware-layers)).

The sequencing rule that prevents the characteristic gesture-start stutter: **gesture start does zero work**. The incoming side shows its retained native pixels (react-freeze keeps native views and last-rendered content alive while suspending React reconciliation ([react-freeze README](https://github.com/software-mansion/react-freeze))); unfreezing happens via one deferred JS task, and the outgoing side's players keep playing through the drag. Only after the spring settles: freeze the now-hidden side, stop scheduling its GL rAF (a boolean — no native teardown), and pause its players staggered one or two per frame (the Bluecadet 50 %→<1 % result again). Two react-freeze cautions gate it: the default placeholder is `null`, which collapses layout if it wraps something that must stay pixel-visible — freeze only the fully-hidden steady state — and a single-sourced report describes a Fabric unfreeze failing to flush, leaving stale content until a touch ([OneKey recipes](https://skills.cat/skills/onekeyhq/app-monorepo/skillshare-skills-1k-ui-recipes)); verify unfreeze-then-swipe-back on both clones before trusting it, and if it misbehaves, fall back to freezing the update *sources* (store subscriptions) instead of the visual tree. Finally, gate commits during the ~300 ms window with a `transitioning` shared value mirrored to a JS ref (a ref write, not a state set): feed effects consult it, buffer updates, and flush in `requestIdleCallback` post-settle — deterministic where `startTransition` is not, since React can still commit mid-window under a transition.

## Measure on the clones: the checks that decide every gated change

The no-root toolkit is `adb shell dumpsys gfxinfo <pkg> reset`, run the scenario, then pull the aggregate and `framestats` — per-frame nanosecond timestamps for every pipeline stage ([archived Android performance testing docs](https://iut-fbleau.fr/docs/android/training/testing/performance.html)). The attribution recipe: high **Animation** stage → too many concurrent UI-thread animators (pause loaders); high **Measure/Layout** → Fabric commits running Yoga mid-scroll (stop committing, use transforms); high **Draw/GPU** → overdraw and invalidation (gradients, blended layers — cross-check with Debug GPU Overdraw, where low-end targets tolerate only ~2.5-3× average ([Kodi skin optimization data](https://kodi.wiki/view/Skin_Optimizations))); high **Sync** → bitmap uploads (oversized images landing during scroll). The crucial blind spot: **gfxinfo cannot see the JS thread** — JS-thread jank appears as *missing* frames with clean per-frame times, confirmed only by a Perfetto trace showing `mqt_js` pegged ([Android Studio jank detection](https://developer.android.com/studio/profile/jank-detection)). Two clone-specific checks cost minutes and can invalidate whole classes of work: `INTENDED_VSYNC` deltas in framestats reveal whether the ROM silently serves the app 30 Hz vsync on a 60 Hz panel — a documented cheap-device power behavior that would make any 60 fps target unreachable until explicitly requested ([bugnet.io 30 Hz report](https://bugnet.io/blog/fix-android-vsync-throttled-to-30hz-on-cheap-displays), single-source, verify) — and `dumpsys SurfaceFlinger` shows whether the wall's SurfaceViews already force GPU client composition, which decides intervention 11 immediately.

Two framing decisions follow from the measurement posture rather than from any single fix. First, a stable lower rate beats an oscillating 60: production RN feeds disable spring physics and shrink list windows on low-end Android to hold stability over peak rate ([Expo blog: Tendbble](https://expo.dev/blog/shipping-a-performance-first-video-feed-how-tendbble-built-a-real-time-social-app-with-expo)), and a 30 fps-source video inside a 60 Hz UI looks intentional where 35-60 oscillation looks broken. Second, build the degradation ladder behind one device-class gate (the `isLowRamDevice()` pattern ([Android Go optimization guide](https://developer.android.com/guide/topics/androidgo/optimize))): smaller windows → posters-first → fewer live decoder slots → simple easing → MB-capped caches purged on `onTrimMemory()` in priority order (video buffers, then decoded images, then data caches). Each rung is individually invisible; the Lite-app evidence is that deleting classes of work outright beats tuning them ([Facebook Lite engineering](https://engineering.fb.com/2016/03/09/android/how-we-built-facebook-lite-for-every-android-phone-and-network/)).

## Conclusion

The report's single most transferable insight is that on this hardware class the budget currency is **decoder instances and main-thread milliseconds, not frames per second** — every intervention that works (pooling, pause-don't-release, poster rotation, on-demand GL, post-settle freezing) is a reallocation of those two currencies, and every intervention that backfires (per-tile players, gesture-start pauses, hardware-texture snapshots, software-decoder fallback) is an accidental overdraft on one of them. The second insight is that the globe fix and the swap fix are *structural*, not incremental: gating the first `endFrameEXP()` and doing zero work at gesture start don't reduce a cost — they make the failure mode impossible, which is why they go first regardless of measurement.

The clone phones invert the usual trust model: vendor-declared codec limits, vsync rates, and HWC behavior are all suspect, so the five on-device checks (codec XML dump, software-decoder logcat watch, SurfaceFlinger composition mode, vsync period in framestats, unfreeze-flush QA) are not optional validation — they are the decision procedure for roughly a third of the list. Land interventions 1-10 as one batch, run the gfxinfo loop before and after, then let the gates admit 11-16 one at a time.
